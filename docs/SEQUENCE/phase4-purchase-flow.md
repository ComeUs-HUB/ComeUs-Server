# Phase 4 — 구매 플로우 (N~P)

> 상태: 미구현 — `domain/cart`, `domain/order`, `domain/payment` 패키지 모두 아직 없음. `ErrorCode`의 Cart/Order/Payment 관련 코드는 [[phase1-global-foundation]]에서 이미 선반영되어 있음

장바구니 → 주문 → 결제로 이어지는 핵심 구매 흐름. [[phase2-auth]](로그인 사용자)와 [[phase3-category-product]](상품/재고)가 먼저 준비되어야 시작할 수 있다.

## N. Cart 도메인 구현

**목적**: 회원별 장바구니를 관리하고 동일 상품 수량 합산, 재고 초과 방어 로직을 구현한다.

**개발 방향**
- 회원 1명당 장바구니 1개(1:1 관계)로 둘지, 다중 장바구니를 허용할지 결정 — 일반적인 커머스 플로우라면 1:1로 충분.
- 같은 상품이라도 옵션(사이즈, 색상 등)이 다르면 별개 항목으로 취급해야 하므로, "동일 항목" 판단 기준(상품ID + 옵션 조합)을 명확히 정의.
- 담기 요청 시 상품 재고를 초과하는 수량인지 사전에 검증 — 이미 `ErrorCode.CART_QUANTITY_EXCEEDED`가 정의되어 있으므로 그대로 활용.

**체크포인트**
- [ ] 동일 상품(+옵션) 재담기 시 수량 합산 확인
- [ ] 재고 초과 수량 담기 시도 시 거부(409)

## O. Order 도메인 구현

**목적**: 주문 생성 시 재고를 안전하게 차감하고, 가격 스냅샷을 저장하며, 주문 상태 흐름을 관리한다.

**개발 방향**
- 동시에 여러 주문이 같은 상품의 마지막 재고를 두고 경쟁하는 상황을 어떻게 막을지 동시성 제어 방식을 결정 — 비관적 락, 낙관적 락+재시도, 또는 재고를 별도 원자적 감소 연산으로 처리하는 방식 등 트레이드오프를 비교.
- 주문 시점의 상품 가격을 스냅샷으로 별도 저장할지 결정 — 이후 상품 가격이 바뀌어도 이미 이루어진 주문의 결제 금액은 유지되어야 하므로 필요성이 높음. 배송지 정보도 마찬가지로 주문 시점 스냅샷이 필요한지 검토.
- 주문 상태 흐름(대기 → 결제완료 → 배송중 → 배송완료 → 취소)을 정의하고, 각 상태에서 허용되는 전환(특히 취소 가능 여부)을 표로 정리 — 배송 중인 주문은 회원이 직접 취소할 수 없도록 막는 규칙에 `ErrorCode.ORDER_CANCEL_NOT_ALLOWED`를 활용.
- 상태를 강제로 변경하는 권한(ADMIN 전용 API)을 별도로 둘지 결정.

**체크포인트**
- [ ] 동시 주문 상황에서 재고가 음수로 내려가지 않는지 확인(동시성 제어 검증)
- [ ] 주문 시점 가격이 이후 상품 가격 변경과 무관하게 유지되는지 확인
- [ ] 배송 중 주문 취소 시도 시 거부(409)

## P. Payment 도메인 구현

**목적**: 결제 요청을 처리하고, 성공 시 주문 상태를 전환하며, 실패 시 재고를 복구하고 환불 로직을 구현한다.

**개발 방향**
- 결제-주문 관계(1:1)를 유지할지, 부분 결제/분할 결제 가능성을 열어둘지 초기 범위를 결정 — 초기 버전은 1주문당 1결제로 단순화하는 편을 권장.
- 외부 PG 연동은 PRD상 미결 사항([[phase7-deployment]] Z 항목 참고)이므로, 실제 PG 없이 Mock으로 우선 구현하되 이후 실제 연동으로 교체하기 쉽도록 결제 처리 로직을 인터페이스로 추상화할지 결정.
- 결제 실패 시 차감했던 재고를 원복하는 흐름과, 중복 결제 시도를 막는 검증(`ErrorCode.PAYMENT_ALREADY_EXISTS`)을 어느 계층(서비스 vs DB 유니크 제약)에서 보장할지 결정.
- 환불 처리 시 결제 상태와 주문 상태를 함께 갱신하고 재고를 복구하는 순서를 명확히 정의.

**체크포인트**
- [ ] 결제 성공 후 주문 상태가 결제완료로 전환되는지 확인
- [ ] 동일 주문에 대한 중복 결제 시도 시 거부(409)
- [ ] 환불 처리 후 재고가 정상적으로 복구되는지 확인
