# Phase 7 — 배포 (T~Z)

> 상태: 미구현 — Dockerfile, docker-compose.yml, `.github/workflows` 전부 부재. 전 도메인 구현이 어느 정도 마무리된 뒤 진행

애플리케이션을 컨테이너화하고, CI/CD로 자동화하고, 실제 서버에 배포·운영하는 단계.

---

## T. Dockerfile 작성

**목적**: 최소 크기의 이미지를 만들어 운영 환경에 배포 가능하게 한다.

**개발 방향**
- 빌드 환경과 실행 환경을 분리하는 멀티 스테이지 빌드를 고려 — 빌드 도구(JDK, Gradle)가 최종 실행 이미지에 남지 않도록.
- 실행 이미지는 JRE만 포함된 경량 베이스를 사용하고, 컨테이너 내부에서 root가 아닌 전용 사용자로 실행되도록 구성해 보안을 강화.
- 운영 프로파일([[phase0-environment-setup]] C 항목, [[phase7-deployment]] V 항목)로 기동되도록 진입점을 설정.

**체크포인트**
- [ ] Docker 이미지 빌드 성공
- [ ] 컨테이너 기동 후 헬스체크 정상 응답
- [ ] 이미지 크기 최소화 확인

---

## U. docker-compose.yml 작성

**목적**: 로컬 개발/단일 서버 배포 시 애플리케이션과 MySQL을 함께 관리한다.

**개발 방향**
- 앱 컨테이너가 DB 컨테이너의 준비 상태를 기다린 뒤 기동되도록 헬스체크 기반 의존성 순서를 구성.
- DB 데이터가 컨테이너 재시작 후에도 유지되도록 볼륨을 분리.
- DB 접속 정보, JWT 시크릿 등 민감 값은 `.env` 파일로 분리하고 반드시 `.gitignore`에 포함.

**체크포인트**
- [ ] DB 준비 전 앱이 먼저 뜨지 않는지 확인
- [ ] 컨테이너 재시작 후에도 데이터 유지 확인
- [ ] `.env` 파일이 Git에 포함되지 않음 확인

---

## V. 환경별 설정 분리 (prod 프로파일)

**목적**: 개발/운영 환경 설정을 명확히 분리해 보안 취약점과 운영 사고를 예방한다.

**구현 현황 — 부분 준비됨**

- `application-prod.yml` 자체는 [[phase0-environment-setup]] C 항목에서 이미 만들어져 있고 `.gitignore`로도 보호되고 있음.
- 다만 actuator 헬스체크(`management.endpoints`) 설정은 아직 없어 이 단계에서 함께 추가해야 함.

**개발 방향**
- 운영 환경에서는 DDL 자동 생성 정책을 안전한 값(검증만 하거나 아예 비활성화)으로, SQL 로그 출력은 끄고, 로그 레벨은 낮춰야 함 — dev/local과 운영의 차이를 표로 정리해두면 실수 방지에 도움.
- 운영 환경변수(DB 접속 정보, JWT 시크릿 등)가 누락된 경우 앱이 조용히 잘못된 값으로 뜨지 않고 바로 실패하도록(fail-fast) 만드는 것을 고려.
- actuator는 필요한 엔드포인트(health, info 정도)만 최소 노출.

**체크포인트**
- [ ] prod 프로파일 실행 시 SQL 로그 미출력 확인
- [ ] 필수 환경변수 미설정 시 앱 기동 실패(빠른 실패) 확인
- [ ] actuator 헬스체크 엔드포인트 노출

## W. CI/CD 파이프라인 구성

**목적**: 코드 Push 시 자동으로 빌드·테스트·이미지 빌드·배포가 실행되도록 한다.

**개발 방향**
- PR 생성 시에는 빌드+테스트만, `main` 브랜치 반영 시에는 이미지 빌드/푸시/배포까지 이어지는 단계별 파이프라인 구조를 고려.
- 빌드 캐시(Gradle 의존성 등)를 활용해 파이프라인 실행 시간을 단축하는 방안을 검토.
- DB 접속정보, 배포 서버 접속키, 컨테이너 레지스트리 인증 정보 등 민감 값은 모두 CI 플랫폼의 시크릿 저장소를 통해 주입 — 코드/워크플로 파일에 직접 노출 금지.

**체크포인트**
- [ ] PR 생성 시 빌드/테스트 자동 실행
- [ ] `main` 브랜치 반영 시 자동 배포 완료
- [ ] 파이프라인 전체 단계 정상 통과 확인

---

## X. 서버 배포

**목적**: 클라우드 서버에 컨테이너 실행 환경을 구성하고 리버스 프록시 + HTTPS를 적용한다.

**개발 방향**
- 애플리케이션 포트는 외부에 직접 노출하지 않고, 리버스 프록시를 통해서만 접근하도록 방화벽 정책을 구성.
- HTTPS 인증서 발급 및 자동 갱신 방식을 결정.
- HTTP 요청은 HTTPS로 강제 리다이렉트되도록 설정.

**체크포인트**
- [ ] 헬스체크 엔드포인트가 HTTPS로 정상 응답
- [ ] HTTP → HTTPS 리다이렉트 동작 확인
- [ ] 애플리케이션 포트 외부 직접 접근 차단 확인

---

## Y. 배포 후 최종 검증

**목적**: 배포된 운영 환경에서 전체 기능이 정상 동작하는지 End-to-End로 검증한다.

**개발 방향**
- 회원가입부터 로그인, 카테고리/상품 등록(ADMIN), 상품 조회(비회원), 장바구니, 주문, 결제, 배송완료 처리, 리뷰 작성, 토큰 재발급, 로그아웃까지 이어지는 시나리오를 순서대로 검증할 수 있는 테스트 시나리오를 마련.
- 전 API 응답이 공통 응답 포맷([[phase1-global-foundation]] D 항목)과 페이지네이션 구조(F 항목)를 일관되게 지키는지 최종 확인.

**체크포인트**
- [ ] 전체 시나리오 통과
- [ ] 응답 포맷 전 API 준수 확인

---

## Z. 운영 모니터링 & 보안 점검

**목적**: 배포 이후 지속적인 운영을 위한 모니터링 체계와 보안 점검 항목을 수립한다.

**개발 방향**
- 로그 보관 기간과 롤링 정책(파일 크기/기간 기준)을 결정.
- 보안 점검 항목: JWT 시크릿의 충분한 길이와 환경변수 주입, 전 구간 HTTPS 강제, JPA 파라미터 바인딩으로 SQL 인젝션 방지, 에러 응답에 스택 트레이스 미노출, 로그인 API에 대한 무차별 대입 방어(Rate Limiting), DB 정기 백업.

**미결 사항 후속 대응 (추후 검토)**
- [ ] Redis 도입 — Refresh Token 저장([[phase2-auth]] I 항목) 및 인기 상품 캐싱
- [ ] 외부 스토리지 연동 — 상품/리뷰 이미지 저장([[phase3-category-product]] M 항목, [[phase5-review]] Q 항목)
- [ ] 외부 PG 연동 — 실제 결제 처리([[phase4-purchase-flow]] P 항목)
- [ ] OAuth2 소셜 로그인 연동
- [ ] 검색 엔진 연동 — 상품 검색 고도화

**체크포인트**
- [ ] 운영 서버 에러 로그 이상 없음 모니터링 체계 확인
- [ ] JWT 시크릿이 소스코드/Git 어디에도 노출되지 않음 확인
- [ ] DB 백업 스크립트 동작 확인
