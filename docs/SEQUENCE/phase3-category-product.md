# Phase 3 — 카테고리 / 상품 (L~M)

> 상태: 미구현 — `domain/category`, `domain/product` 패키지 모두 아직 없음. `ErrorCode`의 Category/Product 관련 코드는 [[phase1-global-foundation]]에서 이미 선반영되어 있음

카테고리 계층 구조와 상품 CRUD·검색을 다루는 단계. [[phase2-auth]]에서 ADMIN 권한 체계가 먼저 확정되어야 CRUD 접근 제어를 걸 수 있으므로 그 이후에 진행.

## L. Category 도메인 구현

**목적**: 대분류/소분류 2단계 계층 카테고리를 구현하고 트리 형태로 반환한다.

**개발 방향**
- 셀프 조인(부모-자식 참조) 구조로 2단계 계층을 표현할지, 별도 대분류/소분류 테이블로 분리할지 결정 — 확장 가능성(3단계 이상 필요해질지)을 고려해 판단.
- 트리 조회 응답 형태(대분류 하위에 소분류 배열을 중첩하는 구조 등)를 프론트엔드와 사전에 합의.
- 하위 카테고리가 존재하는 상태에서 상위 카테고리를 삭제하려는 시도를 막는 방어 로직 필요 — 이미 `ErrorCode.CATEGORY_HAS_CHILDREN`이 정의되어 있으므로 그대로 활용.
- 카테고리 정렬 순서(전시 순서)를 별도 필드로 관리할지 여부 결정.

**체크포인트**
- [ ] 대분류 생성 → 소분류 생성 → 트리 조회 정상 반환
- [ ] 하위 카테고리가 있는 카테고리 삭제 시도 시 거부(409)

## M. Product 도메인 구현

**목적**: 상품 CRUD, 페이징·필터·정렬, 재고 상태 자동 전환, soft delete를 구현한다.

**개발 방향**
- 목록 조회는 [[phase1-global-foundation]] F 항목의 `PageResponse`를 그대로 재사용 — 이 도메인이 사실상 `PageResponse`의 첫 실사용처가 될 가능성이 높음.
- 필터 조건(카테고리, 가격 범위, 키워드 검색)과 정렬 옵션을 어떤 방식으로 조합할지 결정 — 조건 조합이 늘어날 걸 고려해 QueryDSL, JPA Specification 등 동적 쿼리 접근 방식 중 선택.
- 재고가 0이 되면 상품 상태를 자동으로 "품절"로 전환하고, 재고가 다시 채워지면 "판매중"으로 복귀시키는 규칙을 엔티티 책임으로 둘지 서비스 책임으로 둘지 결정. 재고 부족 시 `ErrorCode.OUT_OF_STOCK`을 그대로 활용.
- 상품 삭제는 실제 로우 삭제가 아니라 상태 변경(숨김 처리)으로 처리하는 soft delete 정책을 적용할지 확정 — 주문 이력에 연결된 상품이 삭제되면 안 되므로 [[phase4-purchase-flow]]의 가격 스냅샷 설계와 함께 고려.
- 상품 이미지 저장 방식(로컬 vs 외부 스토리지)은 아직 미결 사항([[phase7-deployment]] Z 항목 참고) — 우선 URL 목록만 저장하는 구조로 시작할지 결정.

**체크포인트**
- [ ] 재고 0 등록 시 자동으로 품절 상태 전환 확인
- [ ] 상품 삭제 시 soft delete(숨김 처리)로 동작하는지 확인
- [ ] 페이징 + 카테고리 필터 복합 조회 정상 동작
