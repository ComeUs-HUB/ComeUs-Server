# 구매 플로우 그림

장바구니부터 결제·환불·복구까지 그림 한 장마다 **핵심 로직만** 요약한다.
계약(API·규칙)은 [domains/purchase/](../../domains/purchase/README.md), 결정 근거는 [ADR](../../decisions/README.md#purchase--장바구니--주문--결제)이 소유한다.

## 구매 플로우 다이어그램 목록

| # | 그림 | 한 줄 요약 |
|---|---|---|
| 0 | [주문 · 결제 전체 흐름](seq-purchase-overview.md) | 재고는 주문에서 확보하고, 돈은 선점에 성공한 승인 한 번으로 확정한다 |
| 1 | [주문 상태](state-order.md) | 7개 상태. 모든 전이는 CAS 하나이고, 토스 호출 중 상태는 취소·배송이 막힌다 |
| 2 | [장바구니 담기](seq-cart-add.md) | `carts` 행 하나를 잠가 동시 담기를 줄 세운다. 재고는 점유하지 않는다 |

| 4 | [결제 승인](seq-payment-confirm.md) | 선점 TX → 토스 승인(트랜잭션 밖) → 반영 TX. 결과를 모르면 되돌리지 않는다 |
| 5 | [결제 게이트웨이](payment-gateway.md) | 토스 응답을 성공 · 확정 거절 · 결과 불명 셋으로만 돌려준다 |
| 6 | [환불](seq-refund.md) | 승인과 같은 모양. 토스 취소가 확인된 뒤에만 재고를 푼다 |

## 모든 그림에 공통인 규칙 네 가지

1. **토스 호출은 항상 트랜잭션 밖에서 한다.** 승인·취소는 DB 롤백으로 되돌릴 수 없다
2. **상태 전이는 CAS(`UPDATE … WHERE status = :expected`) 하나로만 한다.** 0건은 에러가 아니라 "다른 경로가 먼저 처리함"이다
3. **결과를 모르면 되돌리지 않는다.** `*_IN_PROGRESS`로 남기고 복구 배치가 토스에 물어 판정한다
4. **재고는 `PENDING`에서 점유하고 `CANCELLED`로 가는 경로에서만 복구한다** — 결제 전 취소, 15분 만료, 환불 성공

## 각 문서의 모양

모든 문서가 같은 순서다: **한 줄 요약 → 그림 → 핵심 흐름 → 지키는 것 → 실패·경합 → 코드 위치 → Mermaid 원본**.
Mermaid 원본이 그림 내용의 기준이고, PNG는 `src/`의 HTML에서 다시 그린다.
