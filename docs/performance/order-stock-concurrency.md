# 주문 재고 동시성 측정 계획

> 결정 근거는 [ADR 0025](../decisions/purchase/0025-pessimistic-lock-as-stock-concurrency-baseline.md)가,
> 진행 현황은 [roadmap.md](../roadmap.md)가 소유한다. 이 문서는 **무엇을 어떻게 재는가**만 담는다.

재고 동시성 제어를 비관적 락으로 시작하고 측정치로 전환을 판단한다. 네 방식을 같은 부하에서 재고
전환 근거를 숫자로 남기는 것이 목적이고, 그 비교표가 산출물이다.

## 측정 대상

| 방식 | 재고 차감 방법 |
|---|---|
| 비관적 락 | `products` 행을 `FOR UPDATE`로 잠그고 `Product.decreaseStock()` |
| 원자적 감소 | `UPDATE … SET stock = stock - ? WHERE id = ? AND stock >= ?` 한 문장 |
| 분산 락 + DB 차감 | Redisson `RLock`으로 대기를 트랜잭션 밖에 두고 차감은 DB |
| Redis 재고 게이트 | `DECRBY`로 선판정, DB 차감은 뒤따름 |

## 환경

- **MySQL 실기동이어야 한다.** H2는 기본 격리 수준이 READ COMMITTED이고 gap lock도 재현하지 않아
  `./gradlew test`로는 검증되지 않는다 — [ADR 0020](../decisions/purchase/0020-cart-writes-use-read-committed.md)의 선례
- 부하 도구는 k6 또는 Gatling. 수용 기준의 통과/실패가 자동 판정되어야 한다
- 측정마다 **함께 기록할 환경값**: 애플리케이션 인스턴스 수, HikariCP `maximum-pool-size`,
  MySQL `innodb_lock_wait_timeout`, DB 인스턴스 사양, DB까지의 왕복 지연.
  이 값이 없으면 숫자가 재현되지 않는다
- 현재 HikariCP 설정이 없어 풀 크기는 **기본값 10**이다. 측정에서 이 값을 바꿀 때는 바꿨다는 사실을 함께 적는다
- general log·`show-sql`은 끈다 — 쓰기 요청당 수 문장이 추가되어 락 보유 시간을 왜곡한다

## 시나리오

### ① 분산 부하 — 커넥션 풀·CPU 한계

상품 1,000개에 요청을 고르게 흩고 전체 TPS를 올린다. 행 경합이 거의 없는 상태의 상한이므로
②와 비교해 **경합이 만든 손실**을 분리할 수 있다.

### ② 집중 부하 — 상품당 상한과 정합성

상품 1개, 재고 100개에 동시 요청을 올린다(10,000까지). 병목이 DB 행 하나이므로 인스턴스를 늘려도
개선되지 않는 구간이고, 네 방식의 차이가 여기서 갈린다.

## 지표 정의

| 지표 | 정의 |
|---|---|
| 상품당 최대 TPS | 수용 기준(아래)을 모두 통과하면서 p99가 임계 이하인 **최대 도착률** |
| p99 지연 | 주문 생성 API 응답 시간의 99분위 |
| 커넥션 풀 포화 지점 | HikariCP `pending threads`가 0을 벗어나 지속되는 도착률. `CONNECTION_TIMEOUT` 발생은 그 이후다 |
| 음수 재고 | 측정 후 `stock_quantity < 0` 행 수 |
| 과판매 | 성공 주문의 수량 합 − 초기 재고의 초과분 |

**커넥션 풀 포화 지점이 비관적 락의 1차 실패 모드다.** `FOR UPDATE` 대기자가 커넥션을 쥐고
기다리므로, 풀이 비면 상품 조회·로그인 같은 무관한 요청까지 커넥션을 받지 못한다.
처리량 상한보다 먼저 관측될 것으로 보는 지표이고, 네 방식 중 분산 락이 유일하게 겨냥하는 지점이다.

## 수용 기준

통과/실패가 명확해야 한다. 처리량이 목표에 못 미치는 것은 전환 사유이지만, 아래가 깨지는 것은 **버그**다 —
[ADR 0016](../decisions/purchase/0016-stock-reserved-at-order-not-cart.md)이 "음수 재고는 복구가 아니라 버그"로 고정했다.

```
재고 10인 상품에 동시 요청 200건
  → 성공 정확히 10건, P002 거절 190건
  → stock_quantity == 0, 음수 0건, 과판매 0건
  → SOLD_OUT 상태 전환 1회

같은 회원이 같은 멱등키로 주문 요청을 동시에 2건
  → 주문 1건, 재고 차감 1회         (ADR 0024)

주문 생성 중 임의 시점에 프로세스 강제 종료
  → 음수 재고 0건, 커밋된 주문과 차감된 재고가 일치
```

## 부하 클라이언트가 지켜야 할 것

이 셋을 어기면 측정이 조용히 오염된다.

- **요청마다 새 멱등키를 보낸다.** 같은 회원이 같은 키를 재사용하면 두 번째부터 재고를 건드리지 않고
  기존 주문이 반환되어([ADR 0024](../decisions/purchase/0024-order-idempotency-key-in-header.md))
  경합이 측정되지 않는다. 멱등성 자체를 재는 시나리오에서만 키를 고정한다
- **주문 입력은 `cartItemId` 목록이다**([order.md](../domains/purchase/order.md)). 부하 전에 회원·장바구니 항목을
  시딩해야 하고, 주문이 성립하면 그 항목이 삭제되므로 **요청 수만큼 항목이 필요하다.**
  시딩 비용이 측정 규모의 실제 제약이다
- **회원을 분산한다.** 같은 회원의 요청은 `carts` 루트 락에 직렬화되므로
  (ADR 0020) 한 회원으로 부하를 주면 상품 행 경합이 아니라 장바구니 락을 재게 된다

## 결과

측정 후 채운다. 빈 칸은 "아직 재지 않았다"는 뜻이고, 처리량과 정합성을 **같은 표에** 두는 것이 요점이다 —
처리량만 보면 Redis 게이트가, 정합성만 보면 비관적 락이 이긴다.

| 방식 | 상품당 최대 TPS | p99 | 커넥션 풀 포화 지점 | 음수 재고 | 과판매 |
|---|---|---|---|---|---|
| 비관적 락 | — | — | — | — | — |
| 원자적 감소 | — | — | — | — | — |
| 분산 락 + DB 차감 | — | — | — | — | — |
| Redis 재고 게이트 | — | — | — | — | — |

시나리오 ①과 ②를 구분해 기록한다. 측정 후 [ADR 0025](../decisions/purchase/0025-pessimistic-lock-as-stock-concurrency-baseline.md)의
전환 조건에 대조하고, 전환한다면 새 ADR이 0025를 `대체됨`으로 바꾼다.
