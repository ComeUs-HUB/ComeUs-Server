# ADR 0026 — 결제 승인은 트랜잭션 밖에서 호출하고 주문 상태 선점으로 한 번만 진입시킨다

- 상태: 채택 (0028이 보강)
- 일자: 2026-11-04
- 관련: [domains/purchase/payment.md](../../domains/purchase/payment.md), [domains/purchase/order.md](../../domains/purchase/order.md), [ADR 0016](0016-stock-reserved-at-order-not-cart.md), [ADR 0024](0024-order-idempotency-key-in-header.md)

## 맥락

토스 승인 API는 돈을 움직이는 외부 호출이고 DB 트랜잭션으로 되돌릴 수 없다. 승인 뒤 우리 쪽이 롤백해도 청구는 남는다.
호출을 트랜잭션 안에 넣어도 원자성은 생기지 않고, 토스가 느린 동안 커넥션과 행 락만 붙잡는다.

호출을 밖으로 빼면 세 문제가 남는다.

- 같은 주문의 승인 요청이 동시에 오면 **승인 호출이 두 번** 나갈 수 있다
- 호출 뒤 반영 전에 프로세스가 죽으면 **토스는 승인, 우리는 미반영**이 된다
- 승인 거절 뒤 재시도를 허용하므로([payment.md](../../domains/purchase/payment.md)) 주문이 `PENDING`으로 돌아온다.
  상태 값만 비교하면 **늦게 끝난 이전 시도가 새 시도의 선점을 자기 것으로 착각한다**(ABA)

토스 문서는 거절과 결과 불명의 구분, 거절 뒤 같은 `orderId`의 재결제, 같은 `paymentKey`의 재호출 동작을 명시하지 않는다.
그래서 중복 방어를 토스의 동작에 기대지 않는다.

### 현재 설정의 함정

`open-in-view`를 설정하지 않아 Spring Boot 기본값 `true`로 동작한다. 이 경우 트랜잭션이 끝나도 요청이 끝날 때까지
커넥션을 쥘 수 있어, 트랜잭션을 나눠도 승인 호출 중 커넥션 풀이 고갈될 수 있다. 영속성 컨텍스트도 구간 사이에 공유된다.

## 결정

**`POST /api/payments/confirm` 한 요청을 선점·호출·반영으로 나누고, 호출은 트랜잭션 밖에서 한다.
승인 진입은 `orders` 행의 CAS로 한 번만 허용한다.**

```
조율 메서드 ─ 트랜잭션 없음
├─ 선점 TX   주문 조회 → 소유 검증 → 금액 검증 → CAS PENDING → PAYMENT_IN_PROGRESS
├─ 토스 승인 API 호출 ─ 트랜잭션 없음, 자동 재시도 없음
└─ 반영 TX   결과에 따라 전이
```

- 조율 메서드에는 `@Transactional`을 걸지 않는다. 구간은 `TransactionTemplate` 또는 별도 빈으로 나눈다 —
  자기 호출은 프록시를 타지 않아 `@Transactional`이 조용히 무효가 된다
- **`spring.jpa.open-in-view: false`로 끈다.** 커넥션이 호출 구간에 남지 않게 하려는 것이다
- 승인 경로는 `products`를 잠그지 않는다. 거절해도 재고는 점유된 채로 남기 때문이다

### 선점에 `paymentKey`를 함께 저장한다

```sql
UPDATE orders SET status = 'PAYMENT_IN_PROGRESS', payment_key = ?, updated_at = ?
 WHERE id = ? AND status = 'PENDING'           -- 갱신 0건이면 선점 실패

UPDATE orders SET status = ?, updated_at = ?   -- 반영. PAID, 또는 PENDING이면 payment_key도 비운다
 WHERE id = ? AND status = 'PAYMENT_IN_PROGRESS' AND payment_key = ?
```

한 컬럼이 두 문제를 푼다.

- **복구 조회** — 호출 중에 죽어도 `paymentKey`가 남는다. `orderId` 조회는 결제위젯 시크릿 키로 호출할 수 없다
- **ABA** — 반영이 `payment_key`까지 비교하므로 이전 시도는 갱신 0건으로 끝난다

벌크 UPDATE는 `@LastModifiedDate`를 거치지 않으므로 `updated_at`을 문장에 직접 쓴다. 복구 배치의 기준값이다.

### 승인 결과를 셋으로 나눈다

| 결과 | 판정 | 처리 |
|---|---|---|
| 성공 | 2xx | CAS → `PAID`. 1건이면 같은 트랜잭션에서 `Payment(SUCCESS)` 저장 |
| 확정 거절 | 4xx. 단 아래 예외 제외 | CAS → `PENDING`, `payment_key` 비움, 거절 로그 |
| 결과 불명 | 5xx, 타임아웃, 응답 유실, 해석 불가 | 상태 유지. 복구 경로가 판정한다 |

토스 문서에 구분 기준이 없어 보수적으로 정했다. 틀렸을 때의 비용이 비대칭이다 — 불명을 거절로 보면 재시도가
중복 청구가 될 수 있고, 거절을 불명으로 보면 복구 배치가 돌 때까지 재시도가 늦어질 뿐이다.
**"이미 처리됨"을 뜻하는 4xx는 거절이 아니라 결과 불명으로 다룬다.** 응답을 잃고 재호출한 경우 승인이 끝난 결제일 수 있다.

### 복구는 배치로 시작한다

`updated_at` 기준으로 일정 시간 이상 멈춘 `PAYMENT_IN_PROGRESS` 주문을 찾아 `paymentKey`로 토스를 조회한다.

| 토스 상태 | 처리 |
|---|---|
| `DONE` | 성공 반영과 같은 전이 |
| `ABORTED`, `EXPIRED` | 거절 반영과 같은 전이 |
| 그 밖, 조회 실패 | 상태 유지. 다음 주기에 다시 본다 |

- **배치는 요청이 끝난 주문만 판정한다.** 멈춤 판정 시간은 요청 최대 수명보다 길어야 한다.
  짧으면 커넥션을 기다리는 요청을 배치가 앞질러 ABA 경로가 열린다
- 요청 최대 수명을 계산할 수 있도록 커넥션 대기, 토스 호출, DB 작업의 타임아웃을 모두 명시한다.
  타임아웃으로 끝난 요청은 반영하지 않고, 주문은 `PAYMENT_IN_PROGRESS`로 남아 배치가 판정한다
- 인스턴스가 여러 대라 배치가 겹쳐도 CAS가 한쪽만 반영한다. 토스 조회의 중복은 허용한다
- 웹훅은 지금 넣지 않는다. 배치만으로 복구가 성립하고, 웹훅은 복구를 빠르게 할 뿐이다

### 경합의 결말

| 상황 | 결말 |
|---|---|
| 같은 주문의 승인 요청 동시 2건 | 한쪽만 선점. 다른 쪽은 승인 진행 중 응답 |
| 응답을 잃은 재시도, `PAID` + 같은 키 | 기존 결제 반환 |
| `PAID` + 다른 키 | `PAY002` |
| 금액 불일치 | 선점 전에 거절. 호출 없음 |
| 결제창이 열린 사이 주문 만료(`CANCELLED`) | 선점 실패. 호출 없음 |
| 승인 진행 중 주문의 취소 요청 | 거절. 취소는 `PENDING`에 대한 CAS로 한다 |
| 승인은 됐는데 반영 TX 실패 | 상태 유지. 응답은 승인 진행 중. 복구 배치가 `PAID`로 전진 |
| 배치와 요청의 반영 경합 | CAS로 한쪽만 1건. 0건인 쪽은 `Payment`를 저장하지 않음 |
| 타임아웃으로 끊기지 않는 멈춤(GC 정지 등) 뒤 이전 시도의 반영 | `payment_key`가 달라 0건. 새 시도는 보존 |
| 위 경우에 이전 시도의 토스 승인이 성공 | 우리 기록에 없는 청구다. 로그와 알림으로 남겨 취소 처리한다 |

방어선은 CAS, 그 아래 `payments.order_id`·`payment_key` unique다.

## 배제한 대안과 근거

| 대안 | 배제 이유 |
|---|---|
| 호출을 트랜잭션 안에 둔다 | 승인 후 커밋이 실패하면 돈은 빠졌는데 기록이 없다. 토스 지연이 커넥션 풀 고갈로 번진다 |
| 비관적 락으로 승인 구간을 보호한다 | 락은 트랜잭션이 끝나면 풀리므로 호출 구간을 덮으려면 호출을 트랜잭션에 넣어야 한다. 줄 세운 두 번째 요청도 결국 호출한다 |
| Redis TTL 선점 | TTL이 호출보다 먼저 끝나면 상호배제가 깨지고 진행 중이던 증거도 사라진다. DB 상태는 만료되지 않아 배치가 집어낼 수 있다 |
| 결제 후 주문 생성 | 토스가 결제창 전에 `orderId`와 금액을 요구한다. 점유를 미루면 결제 성공 뒤 재고 부족을 알리게 된다([ADR 0016](0016-stock-reserved-at-order-not-cart.md)) |
| 거절 시 `CANCELLED` | 카드만 바꾸면 되는 사용자의 주문이 사라진다 |
| `Payment(FAILED)` 행 저장 | `order` unique가 재시도를 막는다. unique를 성공 결제로 좁히는 것은 MySQL에 부분 인덱스가 없어 생성 컬럼이 필요하다 |
| 선점 표식을 `payments`에 둔다 | 승인 전 행이 생겨 "성공한 결제만 저장"이 깨지고 진행 상태가 두 테이블로 갈린다 |
| 토스 멱등 동작에 기댄 중복 방어 | 이 ADR을 쓰며 읽은 문서에서 동작을 확인하지 못했다. 쓰더라도 우리 DB의 중복은 막지 못한다 |

## 결과 / 되돌리려면

- **[ADR 0024](0024-order-idempotency-key-in-header.md)를 보강한다.** 0024 맥락의 "승인된 `paymentKey` 재승인 거절"은
  확인된 사실이 아니다. 이 ADR은 그 동작을 전제하지 않는다
- `orders`에 `payment_key`, `OrderStatus`에 `PAYMENT_IN_PROGRESS`가 추가된다 — [order.md](../../domains/purchase/order.md)
- 승인 진행 중·금액 불일치·승인 거절의 에러 코드가 필요하다. `PAY002`의 메시지는 진행 중을 덮지 못한다
- **거절 뒤 같은 `orderId`의 재결제가 막혀 있으면** 토스 `orderId`를 시도마다 새로 발급하도록 `orderNumber`와 분리한다.
  선점·호출·반영의 구조와 `payment_key` 비교는 그대로다
- 구현 전 확인할 것은 [roadmap.md](../../roadmap.md)가 소유한다. `open-in-view`를 끄면 앱 전체가 영향을 받는다
- 프로젝트의 첫 스케줄러가 생긴다. `PENDING` 만료·환불·가상계좌는 이 ADR의 범위 밖이다
- 되돌리려면 복구 배치를 대체할 정합 수단을 먼저 마련해야 한다. 호출을 트랜잭션 안으로 되돌리는 경로는 없다
