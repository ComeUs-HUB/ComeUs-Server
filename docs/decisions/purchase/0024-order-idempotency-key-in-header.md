# ADR 0024 — 주문 생성의 중복은 헤더 멱등키와 복합 유니크로 막는다

- 상태: 채택 (0026·0027이 보강)
- 일자: 2026-11-03
- 관련: [domains/purchase/order.md](../../domains/purchase/order.md), [ADR 0016](0016-stock-reserved-at-order-not-cart.md), [ADR 0020](0020-cart-writes-use-read-committed.md)

## 맥락

### 현재 설계가 막는 것과 막지 못하는 것

[ADR 0016](0016-stock-reserved-at-order-not-cart.md)이 재고 점유를 주문 생성으로 옮겼으므로,
**중복 주문은 곧 재고 오차**다. 그런데 주문 생성 경로에는 중복을 막는 장치가 없다.

| 층 | 막는 것 | 수단 |
|---|---|---|
| 주문 생성 | 중복 주문 = 재고 이중 차감 | **없다** ← 이 ADR이 메운다 |
| 결제 승인 | 중복 승인 진입 | 주문 상태 CAS + `payments.order_id` unique |
| PG 호출 | 중복 청구 | PG의 멱등 헤더, 승인된 `paymentKey` 재승인 거절 |

### 문제 — 루트 락은 직렬화하지만 중복을 거르지 않는다

[ADR 0020](0020-cart-writes-use-read-committed.md)의 `carts` 루트 락은 같은 회원의 동시 요청을
순서대로 세울 뿐 **둘 다 성공시킨다.** 주문하기 더블 클릭·타임아웃 재시도·여러 탭이면 이렇게 끝난다.

```
A                                   B
lockByUserId ─ 획득
재고 5 → 4, PENDING 주문 #1 생성
커밋 ─ 락 해제
                                    lockByUserId ─ 대기 후 획득
                                    재고 4 → 3, PENDING 주문 #2 생성
기대: 주문 1건·재고 4        실제: 주문 2건·재고 3
```

uk는 관여하지 않는다 — 서로 다른 주문 행의 INSERT다. 재고는 `PENDING`이 점유하므로([ADR 0016](0016-stock-reserved-at-order-not-cart.md))
사용자가 결제하지 않은 유령 주문이 재고를 잡고, 0016이 "음수 재고는 복구가 아니라 버그"라고 못 박은 것과 같은 급의
정합성 문제가 된다.

클라이언트 재시도는 끊을 수 없다 — 응답을 못 받은 클라이언트는 **주문이 성립했는지 알 수 없으므로** 재시도가 정상 동작이다.
그러므로 서버가 "같은 요청이면 같은 결과"를 보장해야 한다.

## 결정

**주문 생성은 헤더로 받은 멱등키를 `(user_id, idempotency_key)` 복합 유니크로 못 박고,
중복은 거절이 아니라 기존 주문 반환으로 처리한다.**

### 세 층이 각각 다른 일을 한다

```
MVC       헤더 Idempotency-Key 추출 + 형식 검증         "UUID 모양인가"
          @RequestHeader(required = false)
          @NotBlank @Pattern — 클래스에 @Validated

Service   (user_id, key) 조회                          "이미 처리된 요청인가"  ← 대조
  TX1 안   carts 루트 락 직후

DB        uk_orders_user_id_idempotency_key            위 조회를 우회한 경로의 최후 방어선
```

```
┌─ TX1 ─ POST /api/orders ──────────────────────── READ_COMMITTED
│  ① carts 루트 락                       ADR 0020
│  ② (user_id, idempotencyKey) 조회  ← 있으면 그 주문을 반환하고 끝낸다
│  ③ cartItem 검증 → products 락 → 재고 차감 → 주문 저장 → cartItem 삭제
└─ 커밋
```

**조회가 락 뒤에 있는 것이 핵심이다.** [ADR 0020](0020-cart-writes-use-read-committed.md)이 정한
READ COMMITTED 덕에 락을 얻은 뒤의 일반 SELECT가 최신 커밋을 보므로, 두 번째 요청은 첫 번째가 만든 주문을
**확실히 본다**. 락이 순서를 세우고 READ COMMITTED가 최신 읽기를 보장하는 그 맞물림이 여기서 재사용된다.
락 앞에서 조회하면 스냅샷을 읽어 둘 다 통과한다.

**중복은 409가 아니라 기존 주문이다.** 멱등성은 "같은 요청이면 같은 결과"이고, 거절하면 타임아웃 후
재시도한 정상 사용자가 주문을 못 한다. 더블 클릭한 사용자는 두 번째 요청에서 잠깐 기다린 뒤 정상 주문 응답을 받는다.

### 스키마

| 필드 | 타입 | 컬럼 |
|---|---|---|
| `idempotencyKey` | `String` | **NOT NULL**, `length = 64`, `uk_orders_user_id_idempotency_key UNIQUE (user_id, idempotency_key)` |

- **NOT NULL이어야 한다.** MySQL은 nullable 유니크 컬럼에서 NULL 중복을 허용하므로, 선택 항목으로 두면
  키를 보내지 않은 요청에 보호가 **조용히** 사라진다. 누락은 `C001`로 거른다
- **`(user_id, key)` 복합이어야 한다.** 키는 클라이언트가 만드는 값이므로 전역 유니크로 두면
  타인의 키를 선점해 주문 생성을 막는 경로가 생긴다. 복합 유니크가 위조의 피해 범위를 자기 계정으로 묶는다

### uk가 실제로 터지는 경로

②를 우회한 동시 요청은 INSERT에서 제약 위반이 난다. 이때 `GlobalExceptionHandler`의
`DataIntegrityViolationException` 핸들러로 흘려보내면 **`RESOURCE_CONFLICT`(409)가 나가 멱등 원칙이 깨진다.**
`OrderService`가 잡아 **별도 트랜잭션에서 기존 주문을 재조회해 반환**한다 —
그 예외가 트랜잭션을 rollback-only로 표시하므로 같은 트랜잭션에서는 읽을 수 없다.

### `orderNumber`와 합치지 않는다

| | `idempotencyKey` | `orderNumber` |
|---|---|---|
| 만드는 쪽 | 클라이언트 | 서버 |
| 신뢰 | 불신 — 형식 검증 필요 | 신뢰 |
| 쓰임 | 중복 생성 차단 | PG에 넘기는 주문 식별자, 사용자 노출, CS 조회 |

합치면 PG에 넘길 식별자를 클라이언트가 정하게 되고, 사용자에게 보여줄 주문번호가 UUID가 된다.

## 배제한 대안과 근거

| 대안 | 배제 이유 |
|---|---|
| **PK(`id`)를 멱등키로** | ① PK는 전역 유니크라 **소유자 범위를 표현할 수 없다** — 충돌이 "내 중복 요청"이 아니라 "타인의 주문이 이미 존재"가 되고 키 선점 경로가 생긴다 ② InnoDB는 PK가 클러스터 인덱스라 `BIGINT AUTO_INCREMENT` → `VARCHAR(64)`로 바꾸면 삽입 위치가 랜덤해져 페이지 분할이 늘고 모든 secondary index가 커진다. `order_items.order_id`도 `VARCHAR(64)` FK가 되고, `Cart`·`Product`·`User`의 `Long id` + `IDENTITY` 규약에서 `Order`만 이탈한다 ③ 멱등키는 *요청*의 식별자, PK는 *행*의 신원이다 — 수명이 다르다 |
| 바디 필드로 받는다 | 에러 응답이 `FieldError`까지 담겨 품질은 가장 좋다. 그러나 키 생성과 **재시도 간 키 보존**을 화면마다 구현해야 한다 — 멱등성이 깨지는 전형적 원인이 "재시도할 때 키를 새로 만드는 것"이고, 헤더면 그 책임이 FE 인터셉터 한 곳에 모인다. DTO가 전송 메타데이터를 들고, 로깅 시 배송지와 함께 노출된다 |
| 서버가 키를 발급한다 (`POST /api/orders/prepare`) | 위조·선점이 불가능하고 PG가 결제창 호출 전에 주문 식별자를 확정하는 흐름과도 맞다. 그러나 왕복이 한 번 늘고 **발급만 되고 쓰이지 않은 키를 정리할 배치**가 따라온다 — [ADR 0016](0016-stock-reserved-at-order-not-cart.md)이 장바구니 예약을 기각한 것과 같은 모양의 비용이다. 복합 유니크가 클라이언트 생성 키의 위험을 이미 자기 계정으로 묶으므로 지금 범위에서는 과하다 |
| 인터셉터 + Redis 범용 멱등 계층 | 아래 |
| 키를 선택 항목으로 (nullable) | MySQL이 NULL 중복을 허용해 키 없는 요청에 보호가 사라진다. "보낸 요청만 보호된다"는 조용한 실패보다 `C001`로 거르는 쪽이 낫다 |
| 요청 본문 해시(`request_fingerprint`) 즉시 도입 | 같은 키·다른 본문을 잡는 **유효한 보완책**이고 실제 빈틈이다(아래). 다만 정합성 측정 결과를 바꾸지 않으므로 기준선 구현에서는 뺀다 |

### 인터셉터 + Redis 범용 멱등 계층을 지금 넣지 않는 이유

`preHandle`에서 키를 대조해 응답 바디까지 Redis에 저장하는 패턴(Stripe류)은 **대체가 아니라 앞단 캐시**다.

```
이 ADR      =  서비스 조회 + DB 유니크 제약            (권위 있는 검사)
캐시 계층    =  인터셉터 + Redis  +  이 ADR            (그 앞의 캐시)
```

- **크래시 틈이 생긴다.** DB 커밋 후 응답을 Redis에 저장하기 전에 죽으면, `Processing` TTL 만료 후
  같은 키가 "처음 보는 키"로 재실행된다. 이 ADR은 멱등키가 **주문 행과 같은 트랜잭션에서 커밋**되므로
  커밋됐으면 키도 있고 롤백됐으면 키도 없다 — 중간 상태가 존재하지 않는다
- **동시 요청의 결말이 반대다.** Redis `SETNX`는 대기를 제공하지 않아 `Processing`을 만나면 409로 거절한다.
  `carts` 루트 락은 **대기**시킨 뒤 기존 주문을 돌려준다
- **TTL 관리가 필요 없다.** 키의 수명이 주문과 같아 정리 배치가 없다
- Redis가 주문 성공 경로의 전제 조건이 된다. fail-open이면 멱등성이 사라지고 fail-close면 주문이 전면 불가다.
  현재 추가 의존성은 0이다

## 결과 / 되돌리려면

- **같은 키로 다른 본문이 오면 검사하지 않는다 — 알려진 빈틈이다.** 클라이언트가 키를 재사용하면
  다른 항목을 주문하려 했는데 조용히 이전 주문이 반환되고, 사용자는 두 번째 주문이 성립했다고 믿는다.
  보완은 `orders.request_fingerprint`(요청 본문 해시) 컬럼을 더해 키는 같고 지문이 다르면 거절하는 것이고,
  **측정 이후로 미룬다.** 기존 주문의 항목과 요청을 비교하는 방식은 배송지 같은 다른 필드 차이를 못 잡는다
- **응답 바이트 동일성은 보장하지 않는다 — 의도된 차이다.** 기존 주문을 재조회하므로 그 사이 상태가
  `PAID`로 바뀌었으면 응답이 달라진다. 엄격한 멱등성 정의에는 어긋나지만 최신 상태를 주는 쪽이 유용하다
- **FE가 재시도에서 같은 키를 유지해야 성립한다.** 서버만으로 완결되지 않는 유일한 전제이고,
  헤더를 고른 이유가 그 책임을 인터셉터 한 곳에 모으는 것이다
- 스키마는 Order 1단계 마이그레이션(착수 시점의 다음 번호)에 컬럼과 uk를 함께 넣는다
- **대조의 보장이 [ADR 0020](0020-cart-writes-use-read-committed.md)에 의존한다.** 재고 동시성 전략이
  측정 후 바뀌어 `carts` 루트 락이 사라지면 ②의 "확실히 본다"가 무너진다 — 그때 대조를 다시 설계해야 한다.
  DB 유니크 제약은 전략과 무관하게 유효하므로 재고 이중 차감은 계속 막힌다
- 캐시 계층이 값을 하게 되는 조건: ① 멱등이 필요한 엔드포인트가 여러 개로 늘어난다(결제·환불·쿠폰)
  ② 재시도 비율이 유의미하게 높다 ③ **응답 바이트 동일성**이 클라이언트와의 계약이 된다
  ④ Redis가 이미 다른 이유로 운영 중이다. ④가 핵심이다 — 그러면 추가 비용이 코드 몇 개로 떨어진다
- 되돌리려면 중복 주문을 막을 다른 층을 **먼저** 마련해야 한다. 제약만 떼면 재고 이중 차감이 되살아난다
