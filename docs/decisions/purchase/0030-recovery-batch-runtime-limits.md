# ADR 0030 — 복구 배치는 실행 시간에 상한을 두고 판정하지 못한 주문은 건드리지 않는다

- 상태: 채택
- 일자: 2026-11-10
- 관련: [ADR 0026](0026-payment-confirm-outside-transaction.md), [ADR 0028](0028-payment-result-whitelist-and-recovery-limit.md), [ADR 0029](0029-refund-outside-transaction.md), [domains/purchase/payment.md](../../domains/purchase/payment.md), PR #17

## 맥락

[ADR 0026](0026-payment-confirm-outside-transaction.md)·[0028](0028-payment-result-whitelist-and-recovery-limit.md)은 복구 배치가 **무엇을** 판정하는지 정했지만,
9단계 착수 전 프로토타입으로 검증하니 **어떻게 도는지**에 빈틈이 있었다.

- **스케줄러 스레드가 하나다.** Spring Boot 기본 `spring.task.scheduling.pool.size`는 1이다. 복구 배치가 토스 지연으로 길어지면
  `PENDING` 만료 배치까지 멈춰 재고가 풀리지 않는다
- **한 번 실행에 상한이 없다.** 100건을 순서대로 조회하는데 읽기 타임아웃이 30초면, 토스가 응답하지 않을 때 한 번에 최대 50분이 걸린다
- **요청 최대 수명에 상한이 없다.** 판정 시간 5분은 요청 최대 수명보다 길어야 하는데, DB 작업 타임아웃이 없어 수명이 정해지지 않는다.
  커넥션 대기도 선점과 반영에서 두 번 일어나는데 한 번만 셌다
- **판정하지 못한 주문의 `updated_at`이 바뀌면** 1시간 종결 시계가 리셋되어 수동 처리로 넘어가지 않는다. 이 규칙이 문서에 없었다
- **반영 CAS가 0건이면 조용히 끝난다.** 다른 경로가 먼저 반영한 정상 경우와, 토스와 주문이 어긋난 경우를 구분하지 못한다
- **1시간 경보가 매 주기 반복된다.** 1분마다 1시간 넘은 주문을 찾으면 수동 처리될 때까지 같은 주문이 계속 찍힌다

## 결정

**복구 배치의 실행 시간과 요청 수명에 상한을 두고, 판정하지 못한 주문은 행을 갱신하지 않는다.**

| 항목 | 값 | 이유 |
|---|---|---|
| 스케줄러 스레드 | 2 | 복구 배치와 만료 배치가 서로를 막지 않는다 |
| 실행 예산 | 50초 | 다음 주문을 시작하기 전에만 확인한다. 넘으면 남은 건은 다음 주기로 넘긴다 |
| 토스 조회 타임아웃 | 읽기 5초 | 조회는 실패해도 다음 주기에 다시 하면 된다 |
| 반영 트랜잭션 타임아웃 | 10초 | 요청 최대 수명에 상한을 둔다 |

- **처리 중인 주문은 끊지 않는다.** 조회 결과를 받아 놓고 반영하지 못하는 낭비를 피한다. 실제 상한은 50초 + 한 건(약 15초)이다
- **조회 타임아웃은 승인·취소와 따로 둔다.** 승인·취소는 돈이 움직이는 호출이라 짧게 끊으면 결과 불명이 늘어난다. 30초를 유지한다
- **요청 최대 수명은 약 100초다.** 커넥션 대기 30초 × 2 + 토스 호출(연결 3초 + 읽기 30초) + 반영 10초. 판정 시간 5분은 그대로 둔다

### 판정하지 못하면 행을 갱신하지 않는다

조회 실패, `READY`·`IN_PROGRESS`, 검증 불일치처럼 판정하지 못한 주문은 `updated_at`을 포함해 아무 컬럼도 바꾸지 않는다.
1시간 종결 조건([ADR 0028](0028-payment-result-whitelist-and-recovery-limit.md))이 `updated_at`을 기준으로 하기 때문이다.

### 반영 CAS가 0건이면 현재 상태를 확인한다

| 현재 상태 | 뜻 | 처리 |
|---|---|---|
| 목표 상태와 같음 | 요청이나 다른 인스턴스가 먼저 반영했다 | 그대로 끝낸다 |
| 그 밖 | 토스 결과와 주문이 어긋났다 | ERROR, 수동 처리 |

요청 경로의 반영(승인·환불)도 같은 규칙을 따른다. 요청 수명에 상한이 있으면 두 번째 경우는 구조적으로 생기지 않고, 이 확인은 그 전제가 깨졌을 때를 잡는다.

### 1시간 경보는 한 번만 낸다

직전 실행 이후 1시간 경계를 넘은 주문만 ERROR로 남긴다. 판정 중에 생기는 불일치·예상 밖 상태는 WARN으로 낮춘다 —
1시간 경보가 그 주문을 다시 알린다. 인스턴스가 여러 대면 경보가 중복될 수 있고, 이는 허용한다.

## 배제한 대안과 근거

| 대안 | 배제 이유 |
|---|---|
| 복구 배치 전용 스케줄러 빈 | 스레드 풀 크기만 늘려도 서로를 막지 않는다. 작업이 더 늘면 다시 본다 |
| 조회를 병렬로 호출 | 토스가 느릴 때 동시 호출이 늘어 부하를 키운다. 100건 / 5초 상한이면 순차로 충분하다 |
| 실행 예산을 넘으면 처리 중인 주문도 중단 | 조회 결과를 버린다. 정합성 문제는 없지만 다음 주기에 같은 조회를 다시 한다 |
| 판정하지 못한 주문에 시도 횟수 컬럼 추가 | 1시간 종결로 충분하다. 스키마가 늘고 그 컬럼 갱신이 `updated_at`을 건드리지 않게 따로 신경 써야 한다 |
| 경보 여부를 DB에 기록 | 스키마 변경이 필요하다. 인스턴스 메모리로 시작하고 중복 경보는 허용한다 |

## 결과 / 되돌리려면

- `spring.task.scheduling.pool.size: 2`를 설정한다. 스케줄 작업이 늘면 이 값을 함께 본다
- 5초와 50초는 토스 실제 응답 시간을 모르고 잡은 임시값이다. 테스트 키로 응답 시간을 확인한 뒤 조정하고, 바뀌면 이 ADR을 보강한다
- 요청 최대 수명이 바뀌면(커넥션 대기, 토스 타임아웃, 반영 타임아웃) 판정 시간 5분이 여전히 충분한지 다시 계산한다
- 운영 경보 인프라(Phase 7)가 붙으면 ERROR 로그 대신 알림으로 바꾼다
