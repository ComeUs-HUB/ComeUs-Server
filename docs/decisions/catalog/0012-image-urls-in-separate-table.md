# ADR 0012 — 상품·리뷰 이미지는 별도 테이블에 URL만 저장한다

- 상태: 채택
- 일자: 2026-09-15
- 관련: [domains/catalog.md](../../domains/catalog.md), [domains/review.md](../../domains/review.md)

## 맥락

상품과 리뷰 모두 이미지를 **여러 장** 가진다. 정할 것이 둘이었다 —
**DB에 어떻게 매핑할 것인가**, 그리고 **파일 자체를 어디에 둘 것인가**.

두 도메인이 따로 정하면 업로드·삭제 경로가 갈라지므로 **같은 방식으로 정한다**는 것이 전제였다
([catalog.md](../../domains/catalog.md)).

## 결정

**별도 테이블에 URL 문자열만 저장한다.** `product_images`·`review_images`가 각각
부모를 FK로 참조하고, 애플리케이션은 **URL을 다룰 뿐 파일 바이트를 다루지 않는다.**

**스토리지는 로컬로 시작하고, 추후 AWS S3로 옮긴다.** URL만 저장하므로 이전은
저장 위치와 URL 발급 지점의 교체이며 스키마 변경을 동반하지 않는다.

## 배제한 대안과 근거

| 대안 | 배제 이유 |
|---|---|
| `@ElementCollection`으로 컬렉션 매핑 | 결국 별도 테이블이 만들어지지만 **생명주기가 부모에 완전히 묶여** 순서·대표 이미지 같은 속성을 붙이기 어렵다. 어차피 테이블이 생긴다면 엔티티로 두는 편이 낫다 |
| 한 컬럼에 콤마로 이어 붙이기 | 개수 제한·정렬·개별 삭제가 전부 문자열 파싱이 된다 |
| 이미지 바이너리를 DB에 저장(BLOB) | DB 크기와 백업 비용이 커지고, 이미지 전송에 애플리케이션이 끼어든다 |
| 처음부터 S3 | 로컬 개발·테스트에 외부 의존과 자격증명이 필요해진다. URL만 저장하는 구조에서는 나중에 옮겨도 스키마가 그대로다 |

## 결과 / 되돌리려면

- **S3 전환 시 바뀌는 것은 업로드 처리와 URL 발급뿐이다.** 기존 행의 URL은 그대로 두거나
  일괄 치환한다 — 테이블 구조는 건드리지 않는다
- 전환 전까지 이미지 파일은 배포 서버의 로컬 경로에 남으므로, **서버를 새로 띄우면 유실된다.**
  운영 배포([deployment.md](../../deployment.md)) 전에 S3 도입 여부를 확정해야 하는 이유다
- 이미지 삭제는 **행 삭제와 파일 삭제 두 단계**다. 파일 삭제가 실패해도 행은 지워지므로
  고아 파일이 남을 수 있다 — 정리 배치는 필요해지는 시점에 만든다
