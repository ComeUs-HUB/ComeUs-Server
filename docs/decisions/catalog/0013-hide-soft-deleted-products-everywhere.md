# ADR 0013 — soft delete된 상품은 ADMIN에게도 숨긴다

- 상태: 채택
- 일자: 2026-09-16
- 관련: [domains/catalog.md](../../domains/catalog.md), [architecture.md](../../architecture.md)

## 맥락

상품 삭제는 **soft delete**다(`status = HIDDEN`). 주문 이력에 연결된 상품이 사라지면 안 되므로
행을 지우지 않는다 — 카테고리를 하드 삭제로 둔 것과 갈리는 지점이고, 그 근거는 카테고리가
주문 이력에 매달리지 않는다는 것이었다([catalog.md](../../domains/catalog.md)).

그 결과 **지워진 행이 DB에 남는다.** 조회 API가 그것을 어떻게 다룰지는 계약에 없었다.
카테고리는 하드 삭제라 이 질문 자체가 없었다.

정할 것은 둘이었다 — **공개 조회에서 뺄 것인가**, 그리고 **ADMIN에게는 보일 것인가**.

## 결정

**공개 조회 API 전부에서 숨긴다.** 목록에서 제외하고, 상세는 `P001 PRODUCT_NOT_FOUND`(404)다.
**권한으로 분기하지 않는다** — ADMIN이 호출해도 결과가 같다.

단, **읽기 경로에만 필터를 건다.** `update`·`delete`가 쓰는 조회는 `findById`라 HIDDEN까지 읽는다.
이것이 ADMIN이 id만 알면 상품을 되살릴 수 있는 **유일한 통로**이며, 의도된 비대칭이다.
두 조회를 같은 private 헬퍼로 합치면 이 구분이 사라지므로 합치지 않는다.

## 배제한 대안과 근거

| 대안 | 배제 이유 |
|---|---|
| ADMIN에게는 보인다 (권한 분기) | 같은 URL이 권한에 따라 다른 결과를 준다. 컨트롤러가 principal을 받아야 하고, **권한 판정이 필터체인에서 끝나지 않고 서비스로 샌다** — `CategoryController`가 principal을 받지 않는 이유와 어긋난다 |
| `GET /api/admin/products` 분리 | 필터체인이 `hasRole`로 막아 권한 분기가 새지 않는 것은 장점이다. 다만 엔드포인트와 테스트가 늘고 계약 표가 두 벌이 된다. **관리자 화면이 실제로 필요해질 때 추가해도 기존 계약을 깨지 않으므로** 지금 지불할 비용이 아니다 |
| 목록만 숨기고 상세는 허용 | id를 알면 누구나 볼 수 있다. "삭제됐다"는 상태가 URL 추측으로 뚫린다. 주문 내역 화면의 상품 링크가 404가 되지 않는다는 이점이 있으나, 그 화면은 Phase 4에서 주문 스냅샷(`priceAtOrder` 등)을 이미 들고 있다 |

## 결과 / 되돌리려면

- **ADMIN이 HIDDEN 목록을 열람할 수 없다.** 되살리려면 id를 알아야 하고, 현재는 DB에서 찾는다.
  운영이 불편해지면 그때가 관리자 엔드포인트를 추가할 시점이다 — **기존 계약을 깨지 않는 확장**이다
- 필터는 `ProductSpecifications.search()` 안에 **붙박이**로 들어간다. 호출자가 뺄 수 없어야
  새 필터가 추가돼도 정책이 새지 않는다 ([ADR 0011](0011-jpa-specification-for-product-filter.md)이
  "조립을 한곳에 모은다"고 정한 것이 여기서 값을 한다)
- ⚠️ **이 결정이 조용히 뒤집히는 경로가 하나 있다.** `increaseStock()`이 조건 없이 `ON_SALE`로
  되돌리면, Phase 4의 주문 취소·결제 실패가 재고를 복구할 때 **HIDDEN 상품이 목록에 다시 뜬다.**
  그 시점에는 상품 코드를 건드리지도 않으므로 원인을 찾기 어렵다.
  `status == SOLD_OUT`일 때만 복귀시키고, 엔티티 테스트로 고정한다
