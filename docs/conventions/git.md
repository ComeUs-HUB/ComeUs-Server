# Git 규칙

이 저장소의 실제 이력에서 뽑아낸 규칙이다. 새 커밋·브랜치·PR은 여기에 맞춘다.

## 브랜치

```
master              보호 대상. 직접 커밋하지 않는다
feature/<범위>      기능 작업 — 예: feature/phase2-auth
fix/<범위>          단독 버그 수정
```

`<범위>`는 Phase나 도메인 이름을 쓴다(`phase3-category`, `order-concurrency`).
작업이 끝나면 PR을 거쳐 `master`로 합친다.

## 커밋

### ⚠️ 커밋 전 승인을 받는다

**AI 에이전트(Claude Code 등)는 커밋하기 전에 반드시 사용자의 승인을 받는다.**
"작업을 마쳤으니 커밋하겠다"고 임의로 진행하지 않는다.

승인을 요청할 때 아래 셋을 함께 제시한다. 이것만 보고 판단할 수 있어야 한다.

1. **변경 파일 목록** — `git status --short` 또는 `git diff --stat`
2. **커밋 메시지 초안** — 제목과 본문 전문
3. **여러 커밋으로 쪼갤 경우 그 분할안** — 어떤 파일이 어느 커밋에 들어가는지

승인 없이 해도 되는 것은 **읽기 전용 작업뿐이다**(`git status`, `git log`, `git diff`, `git show`).
`add`·`commit`·`push`·`rebase`·`reset`·`merge`는 전부 승인 대상이다.

사용자가 "커밋해줘"처럼 명시적으로 지시하면 그것이 승인이다. 다만 그 승인은 **그 작업 한 번에만**
적용된다 — 이어지는 다음 커밋은 다시 승인을 받는다.

수정을 요청받으면 커밋 메시지만 고쳐 다시 제시하고, 승인 전까지 저장소 상태를 바꾸지 않는다.

### 형식

```
<type>: <무엇을 했는지 한 줄>

<왜 그렇게 했는지. 필요할 때만>
```

**타입**

| type | 쓰는 곳 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 동작 오류 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `test` | 테스트 코드 |
| `docs` | 문서 |
| `chore` | 빌드·도구·무시 목록 등 **소스 밖의 설정** |

`chore`와 `refactor`의 경계: 둘 다 동작을 바꾸지 않지만, `refactor`는 **소스 코드**를 고치고
`chore`는 소스 밖(`.gitignore`, `build.gradle.kts`, 워크플로 파일)을 고친다.
애매하면 `chore`가 아니라 더 구체적인 타입을 고른다 — **분류가 안 되는 변경을 담는 자리가 아니다.**

**제목 규칙**

- 한국어로, **평서형 종결(`~한다`)** 또는 **명사형(`~검증`)**. 과거형("고쳤음")·영어 명령형은 쓰지 않는다
- 무엇을 했는지가 아니라 **무엇이 달라지는지**를 쓴다
  - ❌ `fix: CookieUtil 수정`
  - ✅ `fix: oauth_state 쿠키 경로를 콜백 하나로 좁힌다`
- 단계 작업이면 범위를 앞에 붙인다: `feat: Phase 2 8단계 — 카카오 로그인 API 및 인증 쿠키`

**분할 규칙 (중요)**

- **커밋은 도메인·단계 단위로 쪼갠다.** 여러 도메인을 한 커밋에 섞지 않는다
- **테스트 코드는 구현과 별도 커밋으로 낸다.** `feat` 다음에 `test`가 따라오는 형태
  ```
  feat: Phase 2 9단계 — 회원 API 구현
  test: Phase 2 9단계 — 회원 API와 탈퇴 오케스트레이션 검증
  ```
  구현과 검증이 따로 읽혀야 리뷰에서 "이 테스트가 정말 그 동작을 고정하는가"를 판단할 수 있다

**본문**

한 줄로 이유가 설명되지 않을 때만 쓴다. **배제한 대안이 있으면 본문보다 ADR이 맞다** —
[decisions/](../decisions/)에 남기고 커밋은 짧게 둔다.

## PR

- 제목은 커밋 제목과 같은 규칙
- 본문에 **무엇이 달라지는지 / 왜 / 어떻게 검증했는지** 세 가지를 적는다
- 검증란에는 `./gradlew test` 결과와, 자동 테스트로 덮이지 않는 부분을 무엇으로 확인했는지 쓴다
  (브라우저 E2E 등)
- 리뷰에서 제안받았으나 채택하지 않은 대안은 **ADR로 남긴다.** PR 코멘트에만 두면 사라진다 —
  예: [ADR 0009](../decisions/0009-signup-race-retry-at-login-boundary.md)

## 이슈

`[Phase N] 무엇을 한다` 형태로 제목을 잡고, 본문에 완료 조건을 체크리스트로 적는다.
완료 조건은 "컴파일된다"가 아니라 **무엇을 어떻게 확인하면 끝인지**로 쓴다.
진행 현황 자체는 이슈가 아니라 [roadmap.md](../roadmap.md)가 소유한다.

## 저장소에 들어가면 안 되는 것

`.gitignore`가 막고 있지만, 새 설정 파일을 추가할 때마다 재확인한다.

- `.env`
- `application-local.yml`, `application-prod.yml`
- 그 밖에 `client-secret`·`admin-key`·`JWT_SECRET` 등 비밀값이 든 모든 파일
